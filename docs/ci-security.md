# CI security and dependency ownership

Repository maintainers own review of CI workflows, dependency update pull requests, and the GitHub Actions secrets used by release and publishing jobs. Review workflow changes with the same care as application code because workflow changes can access repository credentials.

External GitHub Actions are pinned to full commit SHAs, with the upstream release version kept in a comment. Dependabot checks GitHub Actions and npm dependencies every Monday. It groups minor and patch updates to keep review manageable; major updates remain separate. A maintainer should confirm the release notes, compatibility, and updated SHA before merging an action update.

Keep `GITHUB_TOKEN` permissions limited to the job that needs them. Grant package write access only to the job that publishes the development image, and keep package consumers read-only. Grant release secrets only to the release step that uses them. Do not print secret values, pass them through command arguments, or expose them to pull requests from forks. If a secret appears in logs or is otherwise exposed, maintainers should revoke or rotate it and review the affected workflow run.

## Dependency advisory review

The lockfile audit reviewed on 29 September 2026 reports four vulnerable dependency entries: two low, one moderate, and one high. The production-only audit reports only Bootstrap's moderate findings. Re-run `npm audit` when reviewing dependency changes because advisory data and the lockfile move independently.

`nodemailer` is a production dependency used by the email job. This branch updates it to 10.0.12, above the 10.0.2 fix for [GHSA-6vj9-mwq6-2f5v](https://github.com/advisories/GHSA-6vj9-mwq6-2f5v). The update is a major-version change from 9.x, so check SMTP delivery and deployment configuration when releasing it. The advisory's credential-disclosure scenario requires direct TLS (`secure: true`), transports sharing a DNS host, and different TLS server names. The job creates transports from one process-level configuration; deployment-specific `local.js` settings are not committed, so maintainers should confirm that no deployment creates per-tenant transports with varying `tls.servername` values.

The production lockfile still contains Bootstrap 3.4.1, which is named by [GHSA-q58r-hwc8-rm9j](https://github.com/advisories/GHSA-q58r-hwc8-rm9j) and [GHSA-vxmc-5x29-h64v](https://github.com/advisories/GHSA-vxmc-5x29-h64v). The checked-in application imports Bootstrap Less for styling and uses React-Bootstrap components; a source search found no Bootstrap JavaScript import, plugin data attributes, or Bootstrap JavaScript asset, so these JavaScript plugin paths do not appear in the current bundle. Keep Bootstrap JavaScript out of the application, and handle replacing Bootstrap 3 and React-Bootstrap 0.33 as a separately tested major migration rather than an automatic version bump.

The high `brace-expansion` findings ([GHSA-mh99-v99m-4gvg](https://github.com/advisories/GHSA-mh99-v99m-4gvg) and [GHSA-rgw5-rvv9-x895](https://github.com/advisories/GHSA-rgw5-rvv9-x895)) are limited in this lockfile to vulnerable 5.0.7 copies nested under development tools (`istanbul-lib-processinfo`, `nodemon`, `nyc`, and `spawn-wrap`). The non-development copy is 1.1.21 and outside the affected ranges. Refresh the development lockfile to patched 5.x releases (5.0.9 or later) and run the toolchain tests; do not treat this finding as a production-runtime advisory.

The low `diff` advisory ([GHSA-73rr-hh4g-fpgx](https://github.com/advisories/GHSA-73rr-hh4g-fpgx)) is also development-only: `diff` 5.0.0 is used by Mocha 8.4.0, with no application runtime import found. Version 5.2.2 is patched within the existing `diff` major; verify Mocha's test output after updating it. npm's automatic fix instead proposes Mocha 12.0.2, a major test-runner upgrade that needs separate compatibility review.
